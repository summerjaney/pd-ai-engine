# PAE v1.9.0 迭代计划

## 版本主题

市场证据驱动的版本决策与效果复盘闭环。

v1.7.0 已形成多需求版本规划能力，v1.8.0 已形成竞品功能证据、人工取舍和候选需求池。v1.9.0 的目标是将竞品、客户反馈、业务数据和内部访谈等输入统一为可追溯的市场证据，并把“证据 → 用户问题 → 需求价值假设 → 版本目标 → 发布后复盘”接入既有需求和版本规划链路。

本版本坚持 PAE 的人工决策原则：系统可以归纳证据、计算建议和提示风险，但不得自动批准需求、自动选择版本范围或自动修改正式产品知识。

## 版本目标

1. 让每个进入版本规划的需求能够回答“为谁解决什么问题、依据是什么、成功如何衡量”。
2. 让版本范围从“需求组合”升级为“有可验证业务目标的需求组合”。
3. 让发布后的实际结果可追溯地回流到需求与下一轮规划，而不污染正式产品事实。
4. 与 v1.6.0 设计单元、v1.7.0 版本组合和 v1.8.0 竞品候选池保持兼容。

## 范围与边界

### 纳入范围

- 市场证据的登记、校验、归档和来源追踪；
- 用户问题、机会点和价值假设的结构化建模；
- 需求、市场证据、问题、假设、预期指标之间的稳定追踪；
- 版本级目标、指标、成功阈值和人工确认门禁；
- 发布后结果录入、偏差分析和下一轮规划建议；
- 脱敏真实业务样例、自动化验收和正式规划交付物。

### 明确不纳入范围

- 自动爬取竞品网站、应用商店或第三方业务系统；
- 自动判断市场结论真实性，或用 AI 替代产品经理批准；
- 实时埋点、数据仓库、BI 平台、CRM 或客服系统连接器；
- 多人协作、审批流、插件市场、自动开发和自动部署；
- 用发布后数据自动改写需求优先级、产品基线或正式知识目录。

外部数据可先通过文件或命令行参数导入；连接器能力留待后续版本，并必须遵守敏感数据和授权边界。

## 核心模型与约束

### 市场证据

新增独立的 `market-evidence` 目录，证据至少包含稳定 ID、类型、来源、采集时间、敏感级别、内容摘要、原始引用定位和 SHA-256 指纹。

首批支持的证据类型：

- `competitor`：复用 v1.8.0 竞品档案中的证据引用；
- `customer-feedback`：客户访谈、工单、销售反馈和调研纪要；
- `business-metric`：脱敏的业务指标、漏斗数据和运营数据；
- `internal-insight`：产品、交付、实施或支持团队的内部判断。

证据没有来源、引用定位、内容指纹或合法类型时不得用于正式价值评估。敏感内容默认仅记录最小必要摘要和引用，不复制进公开交付包。

### 问题、机会与价值假设

新增以下稳定实体：

- `ProblemStatement`：目标用户、场景、现有障碍、影响及证据引用；
- `Opportunity`：待解决的问题集合、受影响范围和置信度；
- `ValueHypothesis`：若交付某项能力，预期为指定对象带来的可测量改善；
- `SuccessMetric`：指标口径、基线、目标阈值、观察窗口和数据来源。

所有问题、机会和假设均必须引用至少一项有效市场证据。AI 只能产出草稿候选；进入正式需求或版本范围前必须由产品经理显式确认。

### 需求价值链

新增 `requirement-value-chain.json`，将需求稳定关联至问题、机会、价值假设、预期指标和证据。正式需求至少需要一项已确认问题和一项已确认价值假设；否则其版本准入状态最高为 `CONDITIONAL`。

使用以下跨成果物追踪标记，补充既有 `[design-unit:*]`、`[platform-knowledge:*]` 等追踪：

- `[market-evidence:<ID>]`
- `[problem:<ID>]`
- `[opportunity:<ID>]`
- `[value-hypothesis:<ID>]`
- `[success-metric:<ID>]`

需求分析、产品概要、PRD、版本范围说明和复盘报告之间的引用缺失，应进入统一设计检查并按严重程度阻断或告警。

## 开发批次

### 第一批：市场证据目录与受控导入

- 建立 `src/market-evidence/`、Schema 和 JSON 校验器，不改变 v1.5.0 真实产品资料目录的现有契约。
- 支持市场证据的新增、查看、列表、校验与脱敏导出。
- 支持将 v1.8.0 竞品分析报告中的有效证据映射为只读市场证据引用，避免复制或重写竞品档案。
- 对来源缺失、重复 ID、无效定位、指纹不一致、非法敏感级别和目录越界进行阻断校验。
- 新增 `pae evidence add/list/show/validate` 命令组。

### 第二批：问题、机会和假设草稿

- 根据已登记的有效证据生成问题、机会和价值假设草稿；首版提供确定性规则实现，并保留可替换 LLM 提取器接口。
- 每个草稿保留其证据引用、推断理由和置信度；未经确认时状态为 `pending`。
- 提供产品经理审核、确认、拒绝和失效机制；证据内容或引用变化后，关联确认自动失效。
- 新增 `pae discovery derive/review/status` 命令组。

### 第三批：需求价值链与工作流接入

- 新增需求价值链服务、追踪校验和面向评审的 Markdown 报告。
- 在 `requirement create` 和复杂需求两段式流程中加载已确认价值链上下文，但不替代现有平台分析、方案选择和设计单元门禁。
- 为需求分析、产品概要、PRD、Review 和正式交付的追踪矩阵补充市场与价值引用。
- 对缺少已确认问题、假设、指标或证据的需求输出明确原因，并将其版本准入限制为 `CONDITIONAL` 或 `BLOCKED`。
- 新增 `pae value link/check` 命令组。

### 第四批：版本目标、指标与范围门禁

- 为 `releases/v{version}/` 新增 `release-objective.json` 和 `release-metrics.md`。
- 每个正式版本必须声明版本目标、目标用户/场景、关联机会、成功指标、基线、目标阈值、观察窗口和负责人。
- 复用 v1.7.0 的版本方案、显式选择、基线与失效检测机制；版本范围或价值链变化后，版本目标确认自动失效。
- 未确认版本目标或任一已纳入需求缺少有效价值链时，`release finalize` 必须拒绝正式交付。
- 新增 `pae release objective/set/check` 命令组或扩展现有 `release` 命令组，最终以不破坏既有 CLI 兼容性为准。

### 第五批：发布后复盘与规划建议

- 支持产品经理录入或从本地结构化文件导入实际指标结果，记录数据来源、观察窗口和录入人。
- 输出预期与实际的差异、未达标风险、可疑假设及后续研究建议；不自动修改优先级、版本基线、产品知识或需求状态。
- 复盘结果作为只读规划输入，在下一次 `portfolio assess` 或 `release plan` 时提供显式参考。
- 新增 `release-retrospective.json`、`release-retrospective.md` 和 `pae release retrospect` 命令。

### 第六批：端到端验收与正式交付

- 构建脱敏“应用级角色与授权体验优化”场景：竞品证据、客户反馈和授权配置完成率共同支撑一个可验证的问题与版本目标。
- 覆盖证据导入、草稿生成、人工审核、需求价值链、版本范围选择、目标确认、发布结果录入和复盘建议全链路。
- 覆盖证据变更、需求修订、版本范围变化、缺少指标、敏感信息脱敏和历史 v1.6—v1.8 回归。
- 生成迭代报告、验收报告、发布前检查报告和含 SHA-256 清单的正式规划交付包。

## 关键门禁

| 门禁 | 触发条件 | 行为 |
|---|---|---|
| 证据有效性 | 缺来源、定位、指纹或类型不合法 | 拒绝进入问题和价值评估 |
| 人工确认 | 问题、机会或假设仍为 `pending` | 不得作为正式需求或版本依据 |
| 需求价值链 | 缺已确认问题、假设或指标 | 需求最高为 `CONDITIONAL` |
| 版本目标 | 缺目标、阈值、观察窗口或负责人 | 阻断 `release finalize` |
| 失效检测 | 证据、需求、范围或指标定义变化 | 对应确认失效，要求重新确认 |
| 发布后复盘 | 实际结果无来源或观察窗口 | 拒绝写入正式复盘 |
| 自动化边界 | AI 推断未人工确认 | 仅输出草稿与建议，不改写正式状态 |

目录编号在实施时须与既有需求交付物编号兼容；如需使用新的阶段目录，不得重命名或覆盖既有正式产物。

## 验收标准

### 自动化验收

1. 有效证据可登记、校验、检索，并保留稳定 ID、来源定位和指纹；无效证据被拒绝。
2. v1.8.0 竞品证据可被只读引用，且竞品分析原文件不被修改。
3. 问题、机会和假设候选均可追溯至有效证据；未确认候选不能进入正式价值链。
4. 已确认的需求价值链能被需求分析、PRD、Review 和版本规划读取并验证引用完整性。
5. 缺少价值链的需求不能以 `READY` 状态进入 v1.7.0 正式版本范围。
6. 缺失版本目标、指标阈值、观察窗口或负责人时，版本正式交付被阻断。
7. 证据、需求、版本范围或指标变化会使相关确认失效，且不会静默覆盖既有正式基线。
8. 发布后结果可生成偏差和建议，但不会自动修改优先级、需求状态、版本基线或正式知识。
9. 敏感证据不出现在默认公开交付包中；导出只保留最小必要摘要与引用。
10. v1.6.0、v1.7.0、v1.8.0 与历史全量自动化测试保持通过。

### 保留人工验收

1. 真实客户反馈、访谈和业务数据的来源合法性及脱敏充分性；
2. 产品经理对问题定义、价值假设、指标阈值与版本取舍的专业判断；
3. 真实 LLM 对复杂、多来源证据的归纳质量；
4. 真实 MasterGo 多页面画布生成与人工可编辑性核验。

## 发布边界

完成六个开发批次、TypeScript 检查、全量自动化测试和正式文档后，才可进入合并、Tag 和 Release 检查。Git 提交、推送、Tag、Release 或任何外部数据连接均需在相应阶段获得明确授权后单独执行。
