## 一、文档目的

本文档不是补写虚假的历史记录，而是基于 Git 全历史搜索结果，从当前版本开始建立明确的验收标准、编号规则和执行基线。

**核心原则**：
- 只记录仓库中能够证明存在的内容；
- 不虚构未使用的编号；
- 编号连续性不能作为测试用例存在的证据；
- 未使用编号允许保留空缺，不得为补齐编号而虚构记录；
- 任何超出 Git 证据范围的绝对结论（如"从未使用"）必须避免；
- 统计口径必须分开，缺陷回归场景不得与自动化测试总数重复累计。

## 九、第四批不能直接沿用无定义记录编号的原因

### 9.1 原因说明

1. **无仓库证据**：TC-001～TC-030 和缺失的 PAE 编号经 Git 全历史确认无定义或使用记录；
2. **无法定义测试用例**：没有历史定义，无法确定这些编号"应该"测试什么；
3. **虚构风险**：如果为这些编号虚构测试用例，会导致验收记录失真；
4. **编号规则冲突**：沿用无定义记录的编号会混淆编号体系。

### 9.2 正确做法

如需扩大验收范围：
1. 根据当前产品需求重新建立测试用例；
2. 使用新的编号段（如 TC-046 开始）；
3. 明确测试目标、输入、预期结果和验收标准。

## 十、重新建立验收用例编号的方案

### 10.1 编号规则

| 编号类型 | 格式 | 用途 |
|---|---|---|
| TC | TC-{序号} | 测试用例编号 |
| PAE | PAE-{版本}-{序号} | 缺陷编号 |

### 10.2 编号使用规则

1. **连续性不强求**：编号允许空缺，不要求连续；
2. **唯一性**：每个编号只能对应一个测试用例或缺陷；
3. **不可复用**：已关闭的缺陷编号不可复用；
4. **新编号段**：新增测试用例使用新的编号段，不填补历史空缺。
